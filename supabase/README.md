# Supabase 데이터 기반

**기반·미리보기·운영자 스키마의 실제 연결을 확인했습니다.** 사용자의 설치 SQL 실행 후 운영 서버 점검에서 운영자 테이블/컬럼이 ready입니다. 실제 계정의 운영자 화면과 영상 전체 흐름은 별도 확인이 필요합니다. 아래 스키마와 RPC는 실제 계정·저장 기능을 연결하기 위한 기반입니다. 공개 키만으로 DDL을 적용할 수 없으므로 올바른 프로젝트의 SQL Editor 또는 관리 권한으로 연결한 Supabase CLI에서 적용해야 합니다. 운영자 관리 화면과 별도 운영자 권한 RPC를 구현했으며 [운영자 안내](../docs/operator-guide.md)에 초기 설정과 사용 순서를 기록했습니다.

## 구조

| 테이블 | 역할 |
| --- | --- |
| `tenants` | 숙소/고객사 |
| `tenant_members` | Supabase Auth 사용자와 고객사 연결, 활성 여부·접근 기간 |
| `assets` | 작업 제목, 지정 승인자, 최신 버전, 계약·권리·수납 상태 |
| `asset_versions` | 원본과 별도 미리보기의 경로·SHA-256, 버전·검토 상태 |
| `version_approvals` | 정확한 버전·승인자·시각·콘텐츠 해시·사용 범위의 변경 불가 이력 |
| `revision_requests` | 특정 버전에 대한 수정 요청과 제작자 처리 시각 |
| `portal_operators` | 고객사 owner와 독립된 활성 제작 운영자 |
| `operator_upload_sessions` | 운영자가 준비한 원본/미리보기 메타데이터와 경로·최신 버전·수정 요청 스냅샷 |
| `operator_action_log` | 고객사 생성·업로드·조건 변경의 변경 불가 감사 기록 |

브라우저의 `authenticated` 역할은 RLS로 허용된 행만 읽습니다. 고객사 멤버십과 파일 접근 계약이 모두 유효해야 작업·버전·승인·수정 이력을 읽을 수 있습니다. 멤버십 목록은 본인 행만 보입니다. 고객사 `owner`도 DB에 직접 쓰거나, 수납·권리·지정 승인자·최신 버전을 바꾸지 못합니다.

고객사·멤버·계약 생성, 수납 확인, 제작 파일 등록은 **별도 신뢰된 운영자 서버**의 책임입니다. 운영자의 인증·권한 확인은 `/api/operator`와 별도 `portal_operators` 권한으로 구현했습니다. Supabase 비밀 키를 브라우저에 전달해서 이 작업을 대신하지 마세요. 가입만으로 고객사나 멤버십을 자동 생성하지 않으며, 확인된 기존 계정에 별도 운영자 권한을 부여해야 합니다. Auth 계정 생성과 초대 메일 발송은 포함하지 않습니다.

## 운영자 RPC 계약

운영자 RPC는 별도의 권한을 확인합니다. `operator_context`, `operator_create_tenant`, `operator_prepare_upload`, `operator_upload_manifest`, `operator_update_asset`는 실제 사용자 JWT와 활성 운영자만 허용합니다. `operator_commit_upload`는 서버가 실제 파일을 검증한 뒤 서비스 역할로만 호출하며 행위자·업로드 작성자·현재 운영자·버전/수정 요청 스냅샷을 재검사합니다. 운영자 브라우저도 기본 테이블이나 운영자 권한에 직접 쓰지 못합니다.

## 고객 RPC 계약

네 함수 모두 `authenticated` 역할에서 **실제 사용자 JWT**로 호출합니다. 사용자 ID나 고객사 ID를 입력으로 받지 않으며, `auth.uid()`로 행위자를 판단합니다. `anon`과 서명 서버의 `service_role`에는 실행 권한이 없습니다.

### `approve_asset_version`

입력: `p_version_id uuid`, `p_channel text`, `p_purpose text`, `p_confirmed boolean`, `p_feedback text = ''`.

출력: `{ "approval_id": "uuid", "version_id": "uuid", "approved_at": "ISO 시각" }`.

접근 가능한 최신 검토 대기 버전의 지정 승인자만 승인할 수 있습니다. 명시적 확인, 미리보기 준비, 유효한 권리 날짜·채널·목적, 미해결 수정 요청 없음, 전달된 수정 초안 없음도 확인합니다. 작성 중인 로컬 초안은 서버가 알 수 없으므로 UI가 `p_feedback`을 함께 전달하고 체크 상태를 관리해야 합니다. 수납은 승인의 선행 조건이 아니며, 최종 다운로드에서 따로 검사합니다.

작업 행과 버전 행을 잠근 뒤 승인 이력 생성과 상태 변경을 한 트랜잭션에서 처리합니다. 동일 버전의 중복 승인, 최신 버전 교체와 경쟁하는 오래된 승인 요청은 거부합니다. 승인 이후에는 해당 버전의 원본과 미리보기 경로·해시·버전 식별자를 바꿀 수 없습니다. 새 파일은 새 버전으로 등록합니다.

### `request_asset_revision`

입력: `p_version_id uuid`, `p_message text` (공백 제외 내용 필수, 최대 4,000자).

출력: `{ "request_id": "uuid", "version_id": "uuid", "requested_at": "ISO 시각" }`.

접근 가능한 최신 검토 대기 버전의 지정 승인자가 요청합니다. 수정 요청과 검토 상태 변경은 원자적으로 처리합니다. 작업당 미해결 요청은 하나입니다. 새 버전을 전달할 때 제작자가 기존 요청의 `resolved_at`을 기록해야 새 버전을 승인할 수 있습니다. 이미 승인한 버전의 재편집 발주는 별도 기능이며 이 RPC 범위에 포함하지 않습니다.

### `authorize_asset_download`

입력: `p_version_id uuid`, `p_channel text`, `p_purpose text`.

출력: `[{ "bucket_id": "staycut-deliverables", "object_path": "고객사UUID/작업UUID/버전UUID/delivery.mp4" }]`.

최신 정확한 승인본인지, 미해결 수정 요청이 없는지, 수납·파일 준비·접근 계약·사용 권리가 유효한지 다시 검사합니다. 멤버 중 지정 승인자가 아닌 사용자도 유효한 권한이 있으면 승인본을 다운로드할 수 있습니다. 승인 이력 자체는 권리 만료나 최신 버전 변경 이후에도 보존합니다.

채널 값은 `instagram`, `youtube`, 사용 목적은 `organic`, `advertising`입니다. 날짜는 클라이언트 입력을 받지 않으며 **서버 시각의 `Asia/Seoul` 날짜**, 시작일·종료일 포함으로 판정합니다. 오류 코드는 `42501`(접근 불가), `55000`(현재 작업 상태/계약 조건 불충족), `22023`(잘못된 입력)입니다.

### `authorize_asset_preview`

입력: `p_version_id uuid`.

출력: `[{ "bucket_id": "staycut-deliverables", "object_path": "고객사UUID/작업UUID/버전UUID/preview/review.mp4" }]`.

활성 멤버십, 멤버십과 작업의 접근 계약 기간, 정확한 최신 버전, `preview_available`과 별도 미리보기 메타데이터를 확인합니다. 내부 검토를 위한 접근이므로 승인·수납·게시용 사용 권리는 선행 조건이 아닙니다. `pending`, `revision_requested`, `approved` 상태 모두 미리볼 수 있으며, 지정 승인자가 아닌 같은 고객사 멤버도 접근할 수 있습니다. 과거 버전·다른 고객사·접근 철회·만료·준비되지 않은 영상은 거부합니다.

미리보기는 `preview_object_path`와 `preview_content_sha256`에 등록한 별도 파일만 반환합니다. 경로는 해당 버전의 `/preview/` 아래여야 하며 원본 경로·해시와 같을 수 없습니다. 두 값은 함께 비우거나 함께 등록하며, 비어 있으면 `preview_available=true`로 바꿀 수 없습니다. 미리보기가 없을 때 원본으로 대체하지 않습니다.

운영자 화면의 업로드 기능을 구현했습니다. 자동 변환은 아직 없습니다. 제작자가 저해상도·워터마크 미리보기를 별도로 만들고 내용과 해시를 확인한 뒤 등록해야 합니다. DB는 경로·해시의 분리를 강제하며 영상의 실제 해상도나 워터마크를 분석하지는 않습니다. 마이그레이션 적용 당시 기존 버전의 미리보기 준비 플래그는 해제됩니다. 이미 승인한 버전은 파일 정보가 잠겨 있으므로 별도 미리보기를 추가하려면 새 버전을 등록합니다.

## 비공개 파일과 서명 서버

`staycut-deliverables` 버킷은 비공개입니다. `storage.objects`의 제한 정책이 해당 버킷에 대한 브라우저 읽기·업로드·수정·삭제를 모두 차단합니다. 다른 포괄적 Storage 허용 정책이 이미 있어도 이 버킷은 차단됩니다. 따라서 브라우저에서 `createSignedUrl`을 직접 호출하는 방식도 사용할 수 없습니다.

Vercel `/api/download`와 `/api/preview`가 사용자 JWT로 각 허가 RPC를 호출하고, 반환된 버킷/경로만 서버 비밀 키로 서명합니다. 비밀 키로 RPC를 호출해 사용자 권한 검사를 대체하면 안 됩니다. 서명 링크 유효 시간은 60초이며, 발급 후 접근을 철회해도 이미 발급된 링크는 남은 유효 시간 동안 작동할 수 있습니다. 민감한 URL을 로그나 영구 데이터에 저장하지 않습니다.

운영자 브라우저는 신뢰된 서버가 허가한 임시 경로에만 직접 업로드합니다. 서버는 실제 파일을 검증하고 고유한 최종 경로로 이동한 뒤 재검증하여 버전을 등록합니다. 파일명은 ASCII 영문·숫자·`_`·`-`·`.`을 사용합니다. 원본은 `고객사UUID/작업UUID/버전UUID/delivery.mp4`, 미리보기는 같은 버전의 `preview/review.mp4`처럼 분리합니다. 각각의 실제 SHA-256을 등록하고 **기존 경로를 덮어쓰지 마세요 (`upsert: false`)**. DB의 승인 이력은 변경을 막지만, 비밀 키로 Storage 파일 자체를 덮어쓰는 운영 실수까지 막지는 못합니다.

## 실제 프로젝트에 적용하기

Supabase 프로젝트 연결·환경 변수 설정을 확인해야 합니다. 서버 비밀 키는 Vercel 서버 환경 변수에만 저장합니다. 운영 데이터가 있는 프로젝트에 테스트용 `bootstrap.sql`을 실행하지 마세요.

Supabase CLI에서 올바른 프로젝트에 연결한 뒤 마이그레이션 이력을 검토하고 `supabase db push`로 `migrations/`의 SQL을 파일명 순서대로 적용합니다. SQL Editor를 사용한다면 기반 마이그레이션 `202610150001_portal_foundation.sql` 다음에 `202610160001_preview_access.sql`을 실행합니다. 이미 적용한 마이그레이션은 다시 실행하지 않습니다. 실제 Auth·Storage 설정, 프로젝트에 이미 있는 권한/정책과의 통합, 사용자 JWT와 파일로 하는 종단 검증은 별도로 수행해야 합니다.

## 회귀 검증

`tests/run.sh`는 **CI의 임시 PostgreSQL 16 DB 전용**입니다. 최소 Supabase Auth/Storage 인터페이스를 테스트 스텁으로 만든 뒤 실제 마이그레이션과 회귀 SQL을 실행합니다. `CI=true`, `PGHOST=127.0.0.1`, `PGPORT=5432`, `PGDATABASE=staycut_test` 외 환경을 거부하며, 기존 `auth`/`storage`/앱 스키마가 있어도 중단합니다.

테넌트 간 격리, 익명·직접 쓰기 금지, 지정 승인자, 정확한 최신 버전, 확인/수정 초안, 계약/권리/수납/파일 조건, 수정 요청 처리, 변경 불가 승인/파일 정보, 비공개 Storage 정책을 검증합니다. 미리보기는 미승인/미수납·수정 요청 상태의 정상 접근과, 다른 고객사·최신 아님·철회/만료·행위자 없음·익명/서비스 역할·파일 준비 안 됨의 거부를 추가 검증합니다. 원본 경로/동일 해시/부분 메타데이터 등록, 준비되지 않은 원본 대체, 승인 후 미리보기 경로·해시 변경도 거부하는지 확인합니다. PostgreSQL 스텁 검증은 실제 Supabase Auth 토큰 발급과 Storage HTTP 동작을 검증하지 않습니다.
